Incremental polling & request economy9.0The periodic tick is a subtree+watermark query (key in tracked OR parent in tracked/epic, updated > watermark) plus a key-in fetch for locally-dirty issues; instance metadata (issue types, start field) is cached per base, the epic config is pulled only on a full sync, and polling pauses while Obsidian is hidden. An idle tick issues no fetch. Covered end-to-end (incremental.test.ts).

Residual risks before live

SevRisk & mitigation
LOWCompany- vs team-managed projects — Validated on a real company-managed project: the full (parent OR "Epic Link") and incremental (key-in OR parent-in) JQL run clean and "Epic Link" resolves. Other project styles still worth a first-run check.
LOWTransition screens / required fields — Validated live: transitions across every issue type had no screen, no required fields, and were global. (If one ever does, the push is held and surfaces as a resolvable conflict, not lost.)
LOWEntity-property round-trip (obsidian-pm / -config) — Confirmed live: the plugin-written obsidian-pm-config sits on the real epic (same setProperty/getProperty path the per-issue milestone bag uses). Milestone bag itself only re-exercises that mechanism.
MEDInbound reconcile against a real instance — The 3-way merge, adopt/push split, and conflict resolution are proven on the mock and by a second client acting as a teammate, but not yet against real Jira: only outbound writes have been exercised live. Worth a deliberate two-sided edit on a throwaway epic before trusting interval sync.
MEDMock fidelity — Every live bug so far passed the suite because the mock had been written to match the connector's assumptions. It now models real instance shapes (priority schemes, a missing Start date field, createmeta envelope variants, XSRF-refused writes, foreign issue types at wrong levels) and each fix was verified by reverting it, but any NEW endpoint the mock hand-rolls carries the same risk until checked against a real payload.
MEDPermissions / rate limits (429) — Failed writes surface as a conflict and retry next sync; no backoff yet. The incremental tick (subtree+watermark, cached metadata, paused while hidden) keeps request volume low, reducing 429 exposure.
LOWConflict resolver UI (no automated DOM test) — The 3-way engine, default picks, and resolveConflict are unit-tested, and the Resolve… flow was manually validated end-to-end (conflict detected → modal → per-field resolve → settled). Still no automated DOM test, so keep an eye on it after modal changes.
LOWDeep hierarchies — Validated 4 levels deep on a real instance; create resolves the issue type by discovered hierarchy level and skips + flags anything nested below the lowest type. Status/priority maps need a one-time tune to the instance's own value names.

Recommended live rollout

  1. Start on a throwaway/low-stakes epic.
  2. Connect and Load project settings; confirm statuses, priorities, assignees, and the epic look right.
  3. Import read-only; confirm hierarchy, dependencies, assignees, and dates.
  4. Export ONE new task; verify type/parent/fields; then edit on both sides and sync.
  5. Confirm a status transition works for your workflow (an "out of sync" flag means it was rejected — open Resolve… to see why).
  6. Deliberately create a conflict: change the SAME field on both sides, sync, then open Resolve… and confirm both "keep mine" and "take Jira" behave.
  7. Only then enable interval sync for the project.
